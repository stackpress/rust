## Proposed mechanism and public surface (for review)

Recommendation: **explicit opt-in execution plus one shared Stackpress setup selector**. This replaces the duplicated store fallbacks and aggregate command loop selection; it does not change Engine::execute_plan or ordinary transactions.

1. In stackpress-sql, add `Engine::execute_non_atomic(&self, queries: &[Query]) -> Result<Vec<QueryResult>>`. Its name/Rustdoc explicitly promise ordered execution outside a transaction and warn that a failure or cancellation can leave effects. Before IO, apply existing query/dialect/budget validation to the list; then use the existing executor in input order and stop at the first failure. Empty scripts return an empty result. A QueryPlan caller retains plan.validate and passes plan.queries(). No new SQL parser, arbitrary batch text, retries or dependency is needed.
2. Add typed, additive progress metadata to SqlError, inspectable as `plan_progress() -> Option<&PlanProgress>` with acknowledged statement count, failed zero-based index and total count. Keep the original error kind, display and cause; no query/bind/connection contents enter automatic output. Successful results remain Vec<QueryResult>. Validation failure has zero effects; a server failure retains its native cause plus the acknowledged prefix.
3. Put the Stackpress-specific selection in `stackpress_framework_sql::setup`: MySQL calls the explicit non-atomic primitive; PostgreSQL/SQLite use the existing atomic plan/transaction execution. Reuse this policy from session/API, aggregate setup commands and the future generated runner. The aggregate would activate its existing framework-sql dependency for its sql feature; any workspace-edge change requires release, with all 699 external tuples unchanged. No new crate or external dependency.
4. Preserve the aggregate's existing public `transaction` function as atomic. Existing store signatures/error shapes stay; progress remains available through the native cause. Existing direct single-statement actions need no transaction wrapper. Source client/history/config skips and force-warning policy remain at their current owners.

These are proposed additive public APIs, not implemented or frozen signatures. QueryPlan cannot currently wrap an arbitrary query slice; the common primitive accepts typed Query values instead. The sequence must not depend on connection-local settings: current setup plans contain ordered typed statements. If implementation finds a source requirement for one pinned native connection, stop for a narrowly reviewed executor/lease grant rather than changing adapter traits speculatively.

Failure semantics: acknowledged statements may already be durable; the failing in-flight statement can have an unknown outcome if its acknowledgement is lost. There is no promise that it was rolled back. Cancellation can leave the same partial state and returns no completed report to the cancelled caller. Never automatically replay, adopt or repair a partial installation. Source install publishes its revision only after all DDL succeeds; uninstall does not remove history. Document these outcomes rather than implying all-or-nothing MySQL setup.

## G27 migration scope change — explicit release needed

**Yes: G48 changes G27's “SQLite migrations only / MySQL application deferred pending journal/repair protocol” boundary.** The current generated runner owns SQLite catalog inspection, writer locking, reconstruction, sequence retention and ledger publication; it is not a backend-neutral executor. G48 authorizes MySQL partial-state semantics, not a claim that those SQLite mechanisms work on MySQL. Existing PostgreSQL generated migration application remains render-only unless separately released; existing PostgreSQL store/aggregate setup stays atomic.

Propose an additive `migrations::MysqlMigrationRunner` using an explicitly supplied native Engine/target and the reviewed typed plan. Reuse immutable history/plan hashing, explicit rename mappings, G37 target/storage checks and exact target-bound loss approval. Generic source force still does not authorize generated destructive plans. Preserve existing SQLite public paths and behaviour, moving backend-neutral approval logic only if necessary with compatible re-exports.

MySQL application must inspect the real target, serialize competing applications for that target, execute steps in order and publish the applied head only after complete success. A failed prefix leaves the prior completed head and visible schema drift; status/reporting must identify that partial state, without automatic repair/adoption/resume. Lost completion acknowledgement is an unknown outcome requiring explicit reconciliation. Define the minimal target ownership/ledger implementation during its released proof; a journal must not be silently presented as already implemented or used to defer G48 indefinitely. Keep the existing app-owned operator commands and SQLite file option intact; add an explicit MySQL binding there, without a new framework/CLI public API.
