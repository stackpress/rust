# Task 00011: G37 explicit string storage length

2026-10-27. **Design proposal; implementation is not released.** G37's explicit-length
principle is accepted; the choices below need coordinator review. This requires a
**generated-schema contract bump from 2 to 3**, coordinated with Slice 8 under G34.
Authority: [G37/G34 and G23 ownership](../decisions.md); previous
[width options](00012-receipt-sql-closeout.md#task-00011-follow-up-mysql-string-key-width-options-only).

## Declaration and normalized form

Use the already reserved `store.*` attribute namespace; the existing Idea parser supports
dotted attributes and rejects duplicate names. Proposed syntax, not implemented:

```idea
model Profile {
  id String @id @store.length(191)
  name String @store.length(255) @max(120)
}
```

Initial eligibility is stored, non-list `String`/`Text` model fields. Refuse the attribute
on embedded fields, virtual relations, lists, enums (including string-backed enums), and
other scalar types. An absent annotation remains TEXT, including MySQL's existing TEXT
key/index refusal. `@max(191)` alone never selects VARCHAR; no default 191 or width profile.

The argument is exactly one positive integer literal, `1..=i32::MAX`; reject flags, zero,
negative/fractional/float/string/null arguments, extra arguments and unknown `store.*` names.
Source JSON uses `"attributes":{"store.length":[191]}`. Add normalized
`Field::storage_length: Option<u32>`; `Some(191)` serializes as `"storage_length":191`,
absence defaults to None and is omitted. Checked conversion supplies `Length::Size(i32)`.
Recheck the range when decoding descriptors/artifacts; never narrow with an unchecked cast.
It is semantic data, retained in fingerprints when raw attributes are scrubbed. Both the
emitted `Store::table()` and `storage_definitions()` must consume the same resolved field.

This changes the public normalized Field and validation semantics: **revision 2 cannot
be extended in place**, even with Serde defaults. Propose schema contract **3**. Keep
UiField's shape unchanged: its existing PublicRule carries the approved length bound,
not a new SQL/charset property. Update framework-admin's pinned `UI_CONTRACT_REVISION`
and its rejection tests together; regenerate all consumers, including admin default/format,
workspace default/matrix/names, pure contracts and quickstart. Mixed generated revisions
must fail compatibility/freshness checks. Strip private storage intent from browser record
snapshots; enforce private bounds in host store guards without publishing private rule args.

## Dialects and character semantics

Select VARCHAR(n) consistently; no new CHECK expression vocabulary in this proposal.

| Dialect | With annotation | Limits and enforcement |
| --- | --- | --- |
| MySQL | `VARCHAR(n)` | utf8mb4; current renderer ceiling 16,383 plus whole-table/index limits below. Native length is in characters. |
| PostgreSQL | `VARCHAR(n)` | Refuse n above 10,485,760 before IO; generated validation prevents overlong values, including excess trailing spaces. |
| SQLite | `VARCHAR(n)` | TEXT affinity; n is **declaration metadata only**. Generated validation/host codec guards enforce it; direct SQL can bypass it. |

This reuses the existing Varchar/Length representation. SQLite does not enforce parenthesized
lengths, so neither successful DDL nor drift inspection proves data within the bound.
TEXT plus CHECK would add constraint/catalog/reconstruction work and a second representation;
it is not needed for G37's permitted declared-length behavior. This limitation must remain
visible in docs and the SQLite proof. [SQLite affinity rules](https://sqlite.org/datatype3.html#affinity_name_examples).

n counts Unicode scalar values (`str::chars().count()`), not UTF-8 bytes, grapheme clusters
or browser UTF-16 units. An emoji may occupy one character/four utf8mb4 bytes; a base letter
plus combining mark counts two. No trimming, normalization, truncation or binary codec.
Admin uses shared validation, not HTML maxlength=n as a substitute. PostgreSQL VARCHAR can
truncate excess spaces; MySQL can do so even in strict mode. Generated values must be
checked before binding; strict mode alone is insufficient. Raw SQL's native coercions are
not an exact-round-trip promise. [PostgreSQL characters](https://www.postgresql.org/docs/18/datatype-character.html),
[MySQL VARCHAR behavior](https://dev.mysql.com/doc/refman/8.4/en/char.html).

## Validation and stored values

Synthesize a canonical `cle(n)` rule after attribute normalization, before validating
defaults; deduplicate an identical explicit rule while preserving its explicit message.
An explicit upper bound may be stricter (the example retains max 120) but must not exceed n.
Reject obvious incompatible static minimum/exact-count bounds; do not claim regex/general
constraint satisfiability. No declaration is inferred in the reverse direction.

Apply the bound to create preparation, provider/default outputs, patch values, upsert and
every batch item before write effects, plus trusted Store encoding and decoding. Nullable
null, empty strings and omitted/unchanged values retain their existing rules. Private/sensitive fields
need host-only guards even when public rule arguments are redacted. Preserve policy before
decoding and existing capability refusals; MySQL RETURNING writes remain unsupported.

## MySQL target facts, index budgets and FKs

Require explicit app-owned target facts for bounded MySQL DDL: InnoDB, DYNAMIC row format,
utf8mb4, a checked collation, and expected InnoDB page size. Do not infer these from connection
charset or silently inherit unverified database defaults. Render explicit engine/row-format/
charset/collation clauses. Use `utf8mb4_bin` in the proof, matching task 00012's existing
fixture; no new global collation default or cross-dialect equality claim. Pin these safe
facts in storage signatures and approval hashes; they are explicit operator expectations,
not discovered width defaults or proof of arbitrary server compatibility. The G26 harness
checks only its own database/table metadata and proves expected limits with boundary DDL
inside its throwaway database; it does not read/change global settings. MySQL application
is not enabled by an asserted target configuration.

Pure planning uses checked arithmetic: each declared utf8mb4 string key part reserves
4*n bytes, summed with supported non-string parts over the **whole** PK, unique index,
secondary index and FK-support index. Check per-part/part-count limits too; never permit
TEXT prefixes or truncate a key. DYNAMIC's full-key budget is 3,072 bytes at page sizes
at least 16 KiB, 1,536 at 8 KiB, and 768 at 4 KiB. Reject unknown target combinations.
Four 191-character parts reserve 3,056 bytes; five reserve 3,820 and refuse at 16 KiB.
Also account for SQL's 65,535-byte row bound, variable-length prefixes/null overhead and
the admitted InnoDB record layout; unknown layouts fail closed. Physical secondary-record
PK overhead is a separate check, not an invented reduction of the declared key limit.
[InnoDB limits](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html).

Resolve every FK against the complete managed catalog before IO. Require identical text
storage family, declared width (including absence), charset and collation across each pair;
do not inherit/copy a missing width from its target. Width equality is G37's stricter policy:
MySQL itself permits differing string lengths, but requires matching charset/collation.
Refuse unsupported external references or a group with inconsistent target facts.
[Native FK restrictions](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html).

## Revisions and migrations

Keep immutable history. New target facts and typed length-preconditions require a proposed
revision/plan artifact format **3**, distinct from schema contract 3. Preserve an explicit
version-2 reader/hash codec for old artifacts; never rewrite/re-hash history through the
new DTO. Existing FieldDto already represents varchar/length; it cannot alone pin the new
target policy/preconditions. Ledger format need not change if its row contract is unchanged.

| Change | Proposed behavior |
| --- | --- |
| No storage change | Existing NoChanges path; validation-only edits never invent a DDL width. |
| n to larger m, or bound removed | Explicit reviewed plan; no truncation. Recheck target row/index/FK admissibility. Removing a MySQL key/index width refuses. |
| TEXT/unbounded to n, or n to smaller m | Narrowing finding, explicit approval of the exact plan hash, and complete existing-value checks; approval cannot waive violations. |
| Charset/collation or non-string retype | Remains refused; width approval does not authorize equality changes or arbitrary conversions. |

SQLite executes width changes by the existing exclusive reconstruction protocol. After the
writer lock and drift/ledger recheck, scan all affected non-null values in finite batches,
validate type and character count in Rust, then copy exact values without casts. Enforce
total row/byte/deadline budgets; incomplete scans refuse before DDL. Do not use SQLite
length() alone: it stops at embedded NUL. Revalidate all FK-linked widths together; preserve
row counts, keys, indexes, FK integrity, AUTOINCREMENT high-water and cancellation/unknown-
commit handling. Reverse widening is a fresh narrowing with a fresh locked check; refuse
if later values no longer fit. No automatic truncation or recovery from discarded data.
[SQLite length semantics](https://sqlite.org/lang_corefunc.html#length),
[existing migration protocol](../slice-6-design-migrations.md).
PostgreSQL/MySQL migrations remain render-only; MySQL apply stays refused.

## Landing ownership and proof after approval

Framework-schema owns normalization, diagnostics, Field/contract 3, fingerprints and public
rules; framework-sql owns shared DDL conversion, private storage guards and versioned migration
planning/checks. Existing `StorageColumn` shapes can stay unchanged; no SQL runtime contract
bump is proposed unless the approved implementation changes that public contract.

**G23 coordination required:** SQL core currently lacks typed MySQL target facts and full
compound-byte guards. Proposed shared work is typed optional DDL storage policy plus checked
rendering/accounting in `sql/src/{schema,ddl,network_ddl,diff}.rs` and its tests, preserving
the existing unannotated/plain Varchar behavior. No raw SQL injection/setter workaround.
Framework-admin's revision gate and all generated admin partitions require its owner's
coordinated update. Task 00012 owns the native harness; no adapter or parser edit is proposed.

| Risk | Required proof |
| --- | --- |
| Lost/implicit width or stale consumer | Idea/JSON equivalence; malformed/type-ineligible declarations; absent width remains TEXT/refused; n affects fingerprints; revision-2/3 and admin mismatch refusals. |
| Character/byte mismatch or private bypass | n/n+1 ASCII, emoji, combining marks, trailing spaces, NUL; defaults/providers, trusted/private encode/decode, patch/batch; public and policy ordering. |
| Oversized/mismatched keys | Compound byte boundary and overflow, small-page facts, row limits, FK width/charset/collation mismatch; recording Database observes zero effects for static refusals. |
| Loss/races during resize | SQLite valid/violating existing data, budget refusal, widen/reverse after new long data, FK groups, sequence preservation, drift/lock/cancel/fault/unknown-commit under kill/reap watchdogs. |
| Render-only evidence mistaken for native support | All-dialect DDL snapshots; real SQLite proof; a separate fully annotated fixture executes its **unchanged generated MySQL DDL** in task 00012's G26 unique throwaway DB and verifies columns/indexes/FKs and text round trips. Retain the legacy TEXT-key refusal case. No generated MySQL RETURNING/CRUD or migration-apply claim. |

After release: regenerate every affected root, run scoped/admin/workspace and browser checks,
four review rounds and honest per-crate coverage (70% development; 90% publication remains
separate). Use one capped/deleted target, no installs/listeners/commits; enable only the
authorized local MySQL harness for the native proof. **Stop here for review:** approve the
syntax/eligibility, revision-3 transition, SQLite declaration-only choice and shared-crate
ownership before any implementation, regeneration, build or database connection.
