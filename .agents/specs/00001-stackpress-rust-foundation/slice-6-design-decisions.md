## Choices for the owner

All rows are open. Each recommendation is a choice to review, not acceptance by silence. The coordinator can ask one short question at a time and record exceptions verbatim in the shared ledger.

| Question | Recommended choice and consequence | Other choice and consequence |
| --- | --- | --- |
| What does the first generated data layer support? | **All ordinary scalar types, enums, nested fieldsets/lists, explicit relations, validation, stores, operations, and SQLite migrations.** Reject unsupported storage/security semantics during generation. ID/random generators need an explicitly registered provider; encryption, password hashing, unusual validators and mixed-type enums have named follow-ups. This gives a useful broad baseline with visible limits. | Include those security/compatibility extensions now. Their algorithms, keys, formats, dependencies and parity proofs need an additional approved milestone before implementation. |
| Where should migration commands live? | **In the independent app-owned codegen/tool binary**, reusing the CLI library's existing `emit` grammar. Pure planning and execution live in framework libraries; the tool alone selects files/credentials and registers maintenance commands. It can bootstrap with generated app files absent. | Add a general migration command to the reusable CLI. That expands the shared CLI's schema/backend knowledge and needs a separate command/config/discovery design; it still cannot depend on an unbuilt generated app. |
| Should generating Rust also create permanent schema history? | **No: explicit revision and migration-plan commands create immutable, reviewable history.** Ordinary generation/check touches only disposable owned Rust output. Removing a model never deletes its historical migration. | Automatically append a revision on generation. Routine experimentation then changes durable history; branching/duplicate revisions and cleanup require an explicit policy. |
| How should renamed fields be recognized? | **Show likely matches, but require an explicit old→new mapping in the migration plan.** Even one same-shaped candidate is not proof of intent. Multiple candidates remain blocked until resolved. | Automatically accept a single same-semantics candidate, matching upstream convenience. This can preserve the wrong field's data when a removal/addition was intended; ambiguity still needs manual resolution. |
| How should destructive upgrades be allowed? | **Refuse by default; accept only the reviewed plan's hash plus an explicit data-loss option.** Generic CLI force and an ambiguity bypass never authorize loss. Invalid conversions, unknown database objects and constraint failures remain errors. | One broad force flag accepts raw drop/add changes as upstream does. It is easier to invoke but couples unrelated CLI force behavior to irreversible data loss. |
| What should going back one revision mean? | **Automatically reverse only changes whose data can be preserved.** Mark other plans irreversible and require a reviewed custom reverse/backfill or backup restoration. Adding then dropping a newly populated column is also potentially destructive. | Emit an automatic reverse for every plan. Recreating a dropped column/table cannot recover its old data, so this would provide schema reversal with explicit data-loss warnings rather than data recovery. |
| How should relations be loaded? | **Explicit include paths, bounded batched loading, and separate typed results.** Base pagination stays correct; no lazy database calls occur when a field is read. Many-to-many uses an explicit join model. | Join every requested relationship into one SQL result. To-many fanout requires extra pagination/deduplication planning and can multiply data; automatic lazy loading risks one query per row. |
| Which operations become externally callable? | **Generate reusable handlers, then require explicit registration and a public-field projection per exposed model.** No HTTP routes or maintenance events are enabled automatically. An app policy owns caller authorization. | Register every model operation/route by default. That makes a schema addition an exposure change and needs an authorization/default-disclosure contract now. |
| What does remove do? | **A model with one Boolean `@active` uses soft remove/restore; ordinary reads exclude inactive records by default.** Hard delete is a separate explicit call; models without `@active` do not receive a soft-remove/restore method. | Make remove hard-delete when no active field exists, matching a common convenience convention. The same method name can then have materially different data-loss behavior across models. |
| How should population run? | **Explicit typed seed steps through one supplied transaction, atomic for database-only steps.** External side effects and arbitrary event dispatch are excluded from that transaction promise. It is never an automatic part of startup/install. | Keep upstream's sequential configured event calls with a partial-progress report. Those calls do not share a transaction automatically and need per-step idempotency for retry. |
| How much network-backend migration support belongs here? | **Prove SQLite execution now; render PostgreSQL/MySQL plans and integrate generated CRUD when Slice 7's adapters are available.** Reject MySQL migration application until a separately reviewed nontransactional DDL/repair protocol exists. | Add resumable MySQL DDL migration execution now. An applied-step journal, locking, partial-failure recovery and live service proofs add a dedicated milestone; a transaction wrapper is insufficient. |

## Existing decisions that are not being reopened

Generation remains ordinary function transforms in listed order, before app compilation, with G20's owned output and `--check`. No `build.rs`, dynamic Rust plugins, new parser, general template engine, or generated Cargo dependency mutation is proposed. Plugin selection is before compilation. Top-level lifecycle and nested dispatch remain G12/G17; Send futures remain required.

The crate layout is the accepted `framework-schema` and `framework-sql` family under `crates/framework/`. Standalone SQL stays domain-agnostic. Browser contracts must not acquire drivers, filesystem tools or server services. No automatic migration, population, HTTP exposure or operation retry follows from registering a database.

| Interface | Agreement or remaining choice for coordinator/owner |
| --- | --- |
| Slice 7 says stores consume Arc<Engine> | Compatible ownership, with a spelling clarification: the host owns/registers Arc<Engine>; pooled DataSession borrows `engine.as_ref()`, and transaction DataSession borrows the exclusive guard. Store code never clones/acquires a SQLx pool. Freeze this borrowed interface instead of requiring every store call to own another Arc. |
| Slice 7 warns about MySQL implicit DDL commit | Aligned: ordinary DML can use transactions; MySQL migration application remains unavailable until a reviewed journal/repair protocol exists. Rendering/CRUD is not migration support. |
| Slice 8 needs five normalized roles, props/aliases and safe inputs | Aligned: Schema owns normalization/selection/precedence, Slice 8 owns compiled component import definitions and actual UI. A tool-only catalog carries Rust import mappings; public UiSchema carries stable component keys only. Public input/access/default flags are specified in the schema contract. |
| Slice 8 asks for precise field/role source spans | A remaining integration proof: current TransformContext passes config without provenance/spans. Propose a declared tool-only DiagnosticMap from existing Composer source/provenance plus existing parser AST spans. M0 must prove imported winning attribute coordinates; normalized JSON inputs may have structural paths only. If exact JSON token spans are required, coordinator must approve that additional source API work. |
| Slice 8 asks about stale updates | Initial key-scoped update is **last writer wins**, with unknown write outcome after timeout/cancel and no automatic retry. No expected-version/optimistic-lock guarantee is proposed. UI must describe that limit; adding compare-and-swap updates is a new owner behavior choice, not an inferred capability. |
| Slice 8 proposes an independent UI tool/shared generated CRUD app | Need one concrete integration choice before M1: recommend its UI/admin transforms join the same app-owned selected registry and owned root; a reusable tools/ui-codegen library may supply functions without becoming a second writer. Recommend sharing the new generated-workspace domain/contracts from its own UI example rather than copying models or altering prior proofs. Separate tools/roots are possible only with explicit partition/contract coordination. |

The only newly exposed owner choices are whether optimistic locking or exact JSON token spans are needed in the first slice, and whether to accept the recommended single app-owned generator composition. Defaults above are proposals; coordinator must reconcile them before releasing dependent UI generation.
