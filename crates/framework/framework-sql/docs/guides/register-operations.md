# Register selected generated operations

Select `emit_stores_with_operations` (or its diagnostics-aware equivalent) in the app-owned generator, and enable `framework-sql/server` in the consuming host. Register an Engine and `Policy(Arc<dyn OperationPolicy>)` during Config. During Listen call `stores::operations::<model>::register(start, &mut registration, prefix, &[Operation::...])`. Retain one `Registration` marker per host; its duplicate check supplements the server's intentionally valid duplicate-listener semantics.

The supported selection is get/detail/search/create/update/upsert/batch/remove/restore/delete. Remove/restore exist only for active models; update/upsert selection is refused for a model without mutable fields. Registration validates required services and selection before adding listeners. It returns ListenerIds for app customization. It adds no HTTP route, CLI command, maintenance event or listener socket. See the app's `operations` test for compiled named handlers through direct calls, nested delegation, CLI and buffered HTTP.

Handlers first honor prior completion/error/body/status, then authorize the selected model and operation. Strict envelopes reject unknown/generated/denied fields, browser-unsafe numbers and malformed input. Host assembly may add private fields but cannot overwrite public inputs or immutable/generated fields. Private defaults are named host providers; omitted fieldset defaults are retained when private members are added. An empty public patch cannot become valid merely because the host supplies private values.

Public responses recursively project approved fields. Caller validation gets safe 400 field issues for approved writable paths, absence gets an explicit 404, policy refusal gets 403, and other failures get sanitized 500. Unknown write outcomes additionally expose `errors.outcome = "unknown"` and a no-automatic-retry message. Concrete policy/schema/SQL causes remain privately traversable; their Display, SQL, binds, credentials and database paths never become public messages. A transaction commit can precede a later serialization/lifecycle failure, so applications must distinguish data acknowledgement from overall response success.
